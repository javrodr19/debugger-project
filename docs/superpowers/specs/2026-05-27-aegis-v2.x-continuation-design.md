# Aegis Debug V2.x — Continuation from `2.0.0-alpha.1` to `2.0.0` GA

**Date:** 2026-05-27
**Status:** Draft — pending review
**Version targets:** `2.0.0-alpha.2`, `2.0.0-alpha.3`, `2.0.0-beta.1`, `2.0.0` (GA)
**Base branch:** `main` (after `v2.0.0-alpha.1-dynamic-validation` merges)
**Target working branches:** one per milestone — see §3.1

---

## 0. Summary

`2.0.0-alpha.1` landed the V2 thesis (runtime-confirmed provenance tier, debug-session
cross-check for null-safety, confidence pill) and the keyboard-driven quick-fix surface
(`AegisQuickFixIntentionAction`). Four of ten V2 roadmap items are done.

V2.x covers the remaining six items, sliced across three more pre-GA milestones plus the
GA cut. The sequencing is driven by what the roadmap calls out as the V2 thesis ("prove
that the findings are real") and by what depends on the V1.5 seams that are already in
place:

| Milestone | Theme | Scope |
|---|---|---|
| **`2.0.0-alpha.2`** | Finish the runtime-tier story | Test-suite cross-check (`AnalysisOrchestrator`), `STATE_BEFORE_INIT` debugger correlation (extend `DebugSessionCoordinator`), native Problems-tool-window emit (`WolfTheProblemSolver`) |
| **`2.0.0-alpha.3`** | Language breadth | Full Python analyzer pipeline (None safety, async flow, complexity, circular deps) registered as a primary tier alongside TS/JS |
| **`2.0.0-beta.1`** | Trust + integration polish | False-positive suppression memory, inspection profile integration (`LocalInspectionTool`), streaming AI responses (`BaseAIService` + JCEF) |
| **`2.0.0`** (GA) | Marketplace cut | Change-notes consolidation, marketplace copy update, verifyPlugin matrix across IU 2024.3.2.2 / 2025.1 / 2026.1, release-quality docs |

The V1.5 refactor is now load-bearing: every V2.x feature below lands in or adjacent to
one of the four extracted collaborators (`AnalysisOrchestrator`,
`DebugSessionCoordinator`, `UIEventRouter`, `FileChangeWatcher`) or in `BaseAIService`.
None of them require touching the facade. That is the V1.5 promise paying off.

## 1. Motivation

V2 is the "trust release" — the static engine has been good enough for 1.x, but every
finding is still labeled with the same generic provenance regardless of whether the
runtime actually exhibits the bug. Users have to take static findings on faith; one
false positive in code they're confident is correct undermines the whole tool.

`2.0.0-alpha.1` proved the mechanic for one signal source (the debugger, for null-safety
only). V2.x extends it across:

- **More signal sources** — the test runner (alpha.2) and the user's own dismissals
  (beta.1).
- **More languages** — Python (alpha.3) is the largest unaddressed language in the
  IntelliJ Python ecosystem that maps cleanly to our existing analyzer interface.
- **More IDE surfaces** — the native Problems panel (alpha.2) and the per-project
  Inspections page (beta.1) so keyboard-driven users aren't forced into the Aegis tool
  window.
- **Better AI ergonomics** — streaming responses (beta.1) replace the "wait then paste"
  feel that V1 shipped with.

The roadmap explicitly says: "V2's dynamic validation should not be sliced or deferred —
false-positive noise is the #1 reason users abandon analysis tools." The alpha.1 cut
proves the mechanism; V2.x must finish the job before GA, or `2.0.0` ships with a half
story and the V2 brand promise is undermined.

## 2. Scope decisions (locked in)

| # | Decision | Rationale |
|---|---|---|
| Q1 | **Four sequential milestones, one branch each.** No bundling across themes. | Each milestone has a different risk profile: alpha.2 touches the debugger and Problems-panel SPIs (low blast radius); alpha.3 is a new-language addition (medium); beta.1 changes the AI streaming model and persistence (medium-high). Splitting per theme keeps revert blast radius local. |
| Q2 | **Test-suite cross-check is the alpha.2 headline.** | It's the other half of the runtime-tier thesis. Without it, runtime confirmation only fires when the user manually debugs, which most users do not do as part of routine work. The test runner fires far more often and produces the same kind of signal (executed line + exception/failure). |
| Q3 | **Python lands as a *primary* tier, not graph-only.** | Roadmap explicitly says "same treatment as TS/JS." Anything less defeats the marketing promise of "V2 = language breadth." A graph-only tier would be a worse user experience than today's Kotlin/Java graph-only mode because Python users would expect the full pipeline. |
| Q4 | **False-positive suppression is *local-only, no telemetry*.** | The privacy-by-default principle in the roadmap is non-negotiable. Suppression memory persists to `~/.aegis/suppressions.json` (per-user, not per-project) so the same dismissed finding stays suppressed across IDE restarts but never leaves the machine. |
| Q5 | **Inspection profile integration extends, does not replace, the existing annotator path.** | The `ExternalAnnotator` already surfaces issues to the editor. Adding `LocalInspectionTool` entries gives users the Settings → Inspections control surface (per-rule severity, scope, enable/disable) without removing the existing path. Both can coexist; the annotator path remains the canonical way Aegis publishes issues. |
| Q6 | **Streaming AI responses are an additive code path, not a replacement.** | `BaseAIService.callModel` keeps its current non-streaming contract. A new `callModelStreaming` returns a `Flow<String>` of token chunks; the UI handlers in `UIEventRouter` decide which to call based on whether the request type benefits from streaming (`explainIssue`, `explainSystem`, `jointFix` explanations all do; `detectIssues` and `suggestFix` JSON responses do not). |
| Q7 | **`STATE_BEFORE_INIT` debugger correlation reuses the alpha.1 evaluator pattern.** | The roadmap lumps "null-safety and state-before-init findings" together for debug-session cross-check. Alpha.1 only shipped null-safety. Alpha.2 adds the second type using the same `XDebuggerEvaluator` path — different filter, same machinery. |
| Q8 | **No platform-floor bump in any V2.x release.** | `sinceBuild = "243.0"` (= 2024.3) was set in V1.3 and stays. The IDE APIs we add against (`WolfTheProblemSolver`, `LocalInspectionTool`, `TestStatusListener`, the Python PSI/PEP support) all exist in 2024.3+ Community Edition. Bumping the floor would break users we explicitly support today. |
| Q9 | **GA `2.0.0` is a marketing cut, not a feature cut.** | No new code lands in `2.0.0` beyond change-notes consolidation, marketplace copy refresh, and a verifyPlugin matrix run. If a feature isn't ready by beta.1, it slips to `2.1.0` rather than holding the GA. |

### 3.2 `2.0.0-alpha.2` — Finish the runtime-tier story

#### Test-suite cross-check

**Home:** `AnalysisOrchestrator` (the V1.5 seam that already owns analysis state and
test seams).

**Mechanism:**

- Register a `TestStatusListener` (the project-level extension point exposed by the
  IntelliJ test runner SPI) at orchestrator init. The listener fires `testStarted`,
  `testFinished`, `testFailed`, and `testIgnored` for each leaf test.
- For each `testFailed` event, the listener carries an `AbstractTestProxy` whose
  `stacktrace` field contains the full Java/JS stack. Parse the stack into
  `(filePath, line)` pairs. For each `(filePath, line)` pair that matches a current
  static finding, mark that finding `RUNTIME_CONFIRMED` with confidence `1.0`.
- For successful test runs, walk the executed-line set (available via coverage SPI when
  the user runs "Run with Coverage"; otherwise this signal is silently skipped). Any
  finding sitting on a covered line that did *not* produce a failure is marked
  `LIKELY` (confidence `0.7`) — covered but not blowing up. Findings on lines never
  covered get a `coverageReached = false` flag (no confidence change; only displayed
  as "needs test coverage" hint per roadmap).

**Why a listener, not a fileWatcher-style poll:** the test runner already publishes the
events; polling JUnit XML output is fragile across runners (JUnit Jupiter, Karma, Jest,
pytest). The `TestStatusListener` SPI is the canonical entry point and handles all of
them uniformly.

**State writes:** through `service.updateIssues(...)` exactly as alpha.1 does.
No new state field on the facade. The runtime confirmation just flips bits on existing
`Issue` records.

#### `STATE_BEFORE_INIT` debugger correlation

**Home:** `DebugSessionCoordinator.performDebugSessionCrossCheck` (alpha.1 method).

**Change:** today the filter is `it.type == IssueType.NULL_SAFETY`. Add
`it.type == IssueType.STATE_BEFORE_INIT` to the filter. The evaluator already returns
the variable's runtime value — for state-before-init, the check is `value == null` *or*
`presentation contains "uninitialized"` (the JDWP "this object has not been
initialized" marker the JVM debugger surfaces). One additional regex on the rendered
presentation string.

**Cost:** ~10 LOC. Pure additive extension of the alpha.1 path.

#### Problems tool window emit

**Home:** a new collaborator, `ProblemsViewCoordinator` (project-scoped service,
registered in `plugin.xml` alongside the other V1.5 collaborators).

**Mechanism:**

- Inject a listener on `GhostDebuggerService.updateIssues(...)` via a hook callback
  (add `private val onIssuesUpdated = mutableListOf<(List<Issue>) -> Unit>()` to the
  facade; `ProblemsViewCoordinator.init` registers itself). This stays consistent with
  the V1.5 single-writer rule — collaborators don't poll, they subscribe.
- On each update, diff the new issue list against the previous one. For each added
  issue, call `WolfTheProblemSolver.getInstance(project).reportProblems(virtualFile,
  listOf(Problem))`. For each removed issue, call
  `clearProblems(virtualFile)` for files whose error count dropped to zero, or re-emit
  the remaining set.
- The `Problem` object carries `description` (issue title), `severity`
  (`HighlightSeverity.ERROR` / `.WARNING` / `.WEAK_WARNING`), and `line`. The native
  Problems tool window then renders our findings alongside compiler + analyzer
  problems.

**Why `WolfTheProblemSolver`, not the newer `ProblemsView` collector API:** Wolf is the
project-level problem store that the Problems tool window subscribes to; using it gives
us per-file grouping for free. The newer `ProblemsCollector` API is more flexible but
also more invasive (we'd need to manage our own provider lifecycle). Wolf matches our
shape — a list of findings keyed by file — with zero adaptation.

**State writes:** none. The coordinator is read-only against `service.issuesByFile`; it
publishes to a platform-owned data structure (`WolfTheProblemSolver`).

### 3.3 `2.0.0-alpha.3` — Python support

**New package:** `com.ghostdebugger.analysis.analyzers.python`.

**Analyzers shipped:** four, mirroring the TS/JS set:

| Rule ID | Type | Mechanism |
|---|---|---|
| `AEG-NONE-PY-001` | `NULL_SAFETY` | PSI walk via `PyExpression` + `TypeEvalContext`. Flag `x.attr` / `x[idx]` when `x`'s inferred type is `Optional[T]` or `Union[T, None]` and no `is None` / `if x` narrowing is in effect at that PSI position. |
| `AEG-STATE-PY-001` | `STATE_BEFORE_INIT` | PSI walk for `self.attr` reads in `__init__` before the matching `self.attr = ...` assignment in the same method. Cross-method state tracking is out of scope for alpha.3 (false-positive bias). |
| `AEG-ASYNC-PY-001` | `UNHANDLED_PROMISE` | Walk `await` expressions; flag `async def` functions that call awaitables without `await` (the classic `forgot to await` bug). Match the TS/JS analyzer's heuristics. |
| `AEG-CYCLE-PY-001` | `CIRCULAR_DEPENDENCY` | Graph already exists from the project graph builder; just extend the import-resolver to handle `import foo`, `from foo import bar`, and relative imports. Cycles use the same iterative DFS that V1.4.1 introduced. |
| `AEG-COMPLEX-PY-001` | `HIGH_COMPLEXITY` | Reuse the existing `ComplexityAnalyzer` regex set; Python's `if`/`for`/`while`/`and`/`or` map cleanly. |

**Fixers shipped:** zero in alpha.3. The deterministic fixer principle is hard to honor
for Python because PSI-validity guarantees in the IntelliJ Python plugin are weaker than
in Kotlin/Java. We surface AI fallback only. Adding Python fixers is V3 scope.

**Symbol extraction:** new `PythonSymbolExtractor` in `parser/`. PEP-based, mirrors the
shape of `KotlinSymbolExtractor`. Pulls function defs, async-def detection, top-level
imports/exports, and rendered short-form types where the Python type system provides
them (PEP 484 / `inspect.signature`).

**Bundled-plugin dependency:**
`bundledPlugin("PythonCore")` added to `build.gradle.kts`. This is Community-Edition
Python, available in IDEA Community 2024.3+. Pro-only Python features (PyCharm
Professional remote interpreters etc.) are out of scope.

**Test infra:** `AegisPythonAnalysisTestCase` base class, mirroring
`AegisKotlinAnalysisTestCase`. Locates `python-core.jar` from the unpacked IDE
distribution at runtime (same pattern as `AegisKotlinStdlibProjectDescriptor`).

### 3.4 `2.0.0-beta.1` — Trust + integration polish

#### False-positive suppression memory

**Home:** new service `SuppressionStore` (application-scoped, not project-scoped — the
suppression is per-user, not per-project, so dismissing a known FP in one project
silences it everywhere the same fingerprint appears).

**Persistence:** `~/.aegis/suppressions.json` (XDG-respecting on Linux, `%APPDATA%` on
Windows, `Library/Application Support` on macOS — use `PathManager.getOptionsPath()` or
the platform's `PersistentStateComponent` and let the IDE manage the path).

**Fingerprint:** `Issue.fingerprint()` already exists from V1.4.1
(`ruleId:filePath:line`). Use it directly. The store maps
`fingerprint → SuppressionRecord(timesShown, timesDismissed, lastConfirmedRuntime,
suppressedAt)`.

**Auto-hide rule:** roadmap says "reported, dismissed by the user, and never
runtime-confirmed across N subsequent analyses." Make `N = 3` and document it as the
default (no settings UI in beta.1; expose as `aegis.suppression.threshold` settings
key for power users). The Issue list in `IssuesContent` gets a "Show N hidden findings"
toggle (default off) that reveals suppressed entries.

**Write hook:** `UIEventRouter` already handles `DismissIssue` events. Beta.1 routes
each dismiss through `SuppressionStore.recordDismissal(fingerprint)`. The dismissal
counter increments; if `timesDismissed >= N` and `lastConfirmedRuntime == null`, the
fingerprint is added to the hide set.

#### Inspection profile integration

**Home:** new package `com.ghostdebugger.inspections`.

**Mechanism:**

- Subclass `LocalInspectionTool` once per language target — `AegisKotlinInspection`,
  `AegisJavaInspection`, `AegisTypeScriptInspection`, `AegisJavaScriptInspection`,
  `AegisPythonInspection` (alpha.3 adds the last one; beta.1 adds the rest).
- Each inspection's `buildVisitor` reads from `service.issuesByFile[file.path]` and
  emits a `ProblemDescriptor` per issue with `LocalQuickFix` entries that delegate to
  `FixerRegistry`. This unifies the quick-fix surface — the same fix you get from
  `Alt+Enter` (via `AegisQuickFixIntentionAction`) is now also offered by the
  inspection.
- Register via `<localInspection>` in `plugin.xml`, with `groupName="Aegis Debug"`,
  `enabledByDefault="true"`, `level="WARNING"`. Per-rule severity comes from the
  user's profile.

**Important:** the inspection path runs on every editor type/edit, so it must be cheap.
It only *reads* from already-populated state (`service.issuesByFile`); it does *not*
trigger analysis. This keeps it within the inspection-tool budget (sub-millisecond per
call).

**Migration:** `AegisQuickFixIntentionAction` stays for now (works without the
inspection profile being enabled). In `2.1.0` we can deprecate the standalone intention
once the inspection path is proven; not in scope for V2.x.

#### Streaming AI responses

**Home:** `BaseAIService` (the V1.5 abstract parent of `OllamaService` /
`OpenAIService`).

**Mechanism:**

- Add `protected abstract suspend fun callModelStreaming(systemPrompt: String,
  userPrompt: String): Flow<String>` alongside the existing `callModel`. Both Ollama
  and OpenAI support SSE for this; Ollama uses its native `/api/generate` stream,
  OpenAI uses `stream: true` on `/v1/chat/completions`.
- Add a public-facing method on the existing `AIService` interface:
  `fun explainIssueStreaming(issue: Issue, contextFiles: List<ParsedFile>):
  Flow<String>`. (Same for `explainSystem` and the *explanation half* of `jointFix` —
  the JSON payload stays non-streamed because we need the full structured response
  before applying a fix.)
- `UIEventRouter` chooses streaming for `ExplainIssueRequested` and
  `ExplainSystemRequested`. As tokens arrive, route them through
  `bridgeChannel().sendStreamingChunk(requestId, chunk)` to the JCEF webview.
- Webview side: new event handler in `DetailPanel.tsx` accumulates chunks into the
  active panel and renders incrementally. No new state machine — the existing
  "explanation" field just gets appended-to.

**Failure mode:** streaming failures fall back to non-streaming `callModel`
automatically, surfaced as a "Switched to non-streaming" toast. The fallback is
transparent and the final rendered answer is identical.

## 4. Risks and mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| `TestStatusListener` events for non-JUnit runners (Jest, pytest) deliver stack traces in formats we can't parse | Medium | Ship alpha.2 with JUnit/Jupiter coverage only; ship pytest + Jest stack-trace parsers as additive in `2.1.0` if user demand exists. The runtime-tier marker just stays absent for unsupported runners — it's not a regression. |
| `WolfTheProblemSolver` SPI changes between IU 2024.3 and 2026.1 cause Problems-panel emit to silently break on one IDE | Low | The verifyPlugin matrix already covers all three IDEs; CI catches the break before merge. The fallback (no Problems emit, our tool window still works) is graceful. |
| Python analyzer false-positive rate is higher than TS/JS because the PEP type system is weaker | Medium-high | Hold to the conservative-miss bias: when `TypeEvalContext` returns `Any` or an unresolved symbol, do not flag. Document the bias prominently in the Python analyzer's KDoc. The V1.2 false-positive-trust-loss lesson applies double here. |
| Suppression memory grows unbounded over years of use | Low | Cap the file at 10,000 records; LRU-evict by `suppressedAt`. The user's history of dismissed FPs across that many findings already exceeds practical recall anyway. |
| Streaming AI responses cause the webview to over-paint and stutter | Medium | Throttle token chunks to one render per 16ms (one frame). The accumulator string is mutated freely; only the React `setState` is rate-limited. |
| Inspection-tool budget exceeded if `service.issuesByFile` is recomputed on every visitor call | High if implemented naively | The visitor is read-only. The map is pre-grouped in `updateIssues`. The visitor just does an `O(1)` map lookup followed by an `O(k)` iteration over the file's already-grouped issues, where `k` is small. Profile in beta.1 to confirm. |

## 5. Non-goals (out of V2.x scope)

The following items appear in the V2 roadmap section but are deferred to V3+ for the
stated reason:

- **Custom rule authoring** — V3 scope, explicit roadmap deferral.
- **Six more deterministic fixers** — V3 scope.
- **Profiler correlation** — V4 scope.
- **Cross-repo graph** — V5 scope.
- **Python fixers** — too risky without PSI-validity guarantees in the Python plugin;
  deferred to V3 when the fixer interface is being extended anyway.
- **Pytest/Jest stack-trace parsers** — additive on top of JUnit; if marketplace
  feedback warrants, lands in `2.1.0`, not `2.0.0`.
- **Pro-only Python features** (remote interpreters etc.) — out of scope; Community
  Edition only.

## 6. Open questions

1. **Suppression UX in the toolbar.** Beta.1 ships the "Show N hidden findings" toggle
   inline with the issue list. Do we also want a "manage suppressions" page in
   Settings? Not in beta.1; revisit if users complain about hidden findings they can't
   un-suppress without manually editing the JSON.
2. **Streaming chunk granularity for Ollama.** Ollama's stream API emits one token per
   chunk by default. Sending one JCEF event per token may be expensive. Decision:
   batch on the Kotlin side into ~40-character chunks before bridging, deferred to
   beta.1 implementation phase.
3. **Wolf vs ProblemsCollector.** If `WolfTheProblemSolver` is in a long deprecation
   cycle in 2026.x, switch to `ProblemsCollector`. Verify at alpha.2 implementation
   time; both share the same shape so the switch is local.
