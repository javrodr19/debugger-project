**Date:** 2026-04-27
**Status:** Approved — ready for implementation plan
**Version target:** `1.3.0` (bundled release, mirrors V1.2 pattern)
**Base branch:** `main`

## 0. Summary

V1.3 makes Aegis Debug a first-class K2-mode citizen and uses the Kotlin Analysis API to deliver substantially better Kotlin findings. It is one bundled release with six dependency-ordered commits:

1. Bump `sinceBuild` to `"243.0"` and `verifyPlugin` matrix to 2024.3.2.2 / 2025.1 / 2026.1.
2. Migrate Kotlin code paths from synthesized PSI (`PsiFileFactory.createFileFromText`) to project-bound PSI (`PsiManager.findFile(virtualFile)`); introduce the `KotlinAnalyzer` base class and `withKtAnalysis` helper. Behavior-preserving.
3. Rewrite `KotlinNullSafetyAnalyzer` on the Analysis API. Same rule ID, better findings.
4. Add three new analyzers: `KotlinUnsafeCastAnalyzer` (`AEG-CAST-KT-001`), `KotlinTypeMismatchAnalyzer` (`AEG-TYPE-KT-001`), `KotlinRedundantLetAnalyzer` (`AEG-REDUNDANT-LET-KT-001`).
5. Add two deterministic fixers: unsafe-cast (`as` → `as?` + Elvis) and redundant-let (unwrap). Type-mismatch is analyzer-only.
6. Enrich `FunctionSymbol` with `returnType: String?` and `paramTypes: List<String>`; populate from Kotlin (Analysis API) and Java (PSI directly) extractors. NeuroMap and AI prompts consume the new fields when present.

V1.2 shipped at 117 green tests with `verifyPlugin` Compatible across IU 2023.2.6 / 2024.1.6 / 2024.3.2.2 / 2025.1. V1.3 must preserve a green bar and a Compatible verdict against the new (raised) matrix.

## 1. Motivation

V1.2 already declared `<supportsKotlinPluginMode supportsK2="true"/>` in the manifest as a quick-fix for the IDE-shown incompatibility banner. That declaration was *honest* (the V1.2 code uses only Kotlin PSI, not K1-only resolution APIs) but it left two latent quality ceilings:

- **Name-based null-safety matching.** `KotlinNullSafetyAnalyzer` flags accesses by syntactic match. It misses every type-inferred nullable (`val x = repo.find()` where `find(): T?`) and produces false positives where a `?`-typed property is reassigned to a non-null value before access. The author's own KDoc acknowledges this: *"Name-based matching only (no Kotlin BindingContext) — the cost of full resolution isn't justified for single-file scope."* That cost equation flips with the K2 Analysis API, which is stable, IDE-managed, and cheap at file granularity.
- **Synthesized PSI everywhere.** Both `KotlinNullSafetyAnalyzer` and `KotlinPsiSymbolExtractor` build a fresh sandboxed `KtFile` per analysis via `PsiFileFactory.createFileFromText`. This was a deliberate test-friendly choice in V1.0/V1.2 but it precludes any semantic resolution — synthesized files aren't bound to a `KaSourceModule`. Migrating to project-bound PSI is the single largest unblock for V1.3 and beyond.

The Kotlin Analysis API (`org.jetbrains.kotlin.analysis.api.*`) ships bundled with the Kotlin plugin, requires no new Gradle dependency, and is the platform-blessed replacement for the now-forbidden `BindingContext` / `analyzeAndGetResult`. It exposes types, smart-casts, symbol resolution, and nullability through `analyze(file) { ... }` blocks scoped to a read action. V1.3 adopts it.

The roadmap places "language breadth" in V2 and "fixer breadth + custom rules" in V3. V1.3 sits cleanly between them as **the Kotlin quality release** — same rule surface (one rewritten + three new analyzers, two fixers), measurably better findings on Kotlin code, and the platform plumbing for V2/V3 to extend without revisiting the Analysis API question.

## 3. Architecture

### 3.1 File resolution: synthesized → project-bound

Every Kotlin code path replaces:

```kotlin
val ktFile = PsiFileFactory.getInstance(project)
    .createFileFromText("Sample.kt", KotlinLanguage.INSTANCE, content) as? KtFile
```

with:

```kotlin
val ktFile = PsiManager.getInstance(project).findFile(parsedFile.virtualFile) as? KtFile
```

The `virtualFile` field has been on `ParsedFile` since V1.0 — it has simply been ignored by Kotlin call sites. The synthesized-PSI path is **deleted entirely.** No fallback. Files outside content roots (scratch files, etc.) silently skip Aegis Kotlin analysis; this matches Aegis's contract — every analysis path starts from `FileScanner` walking the project, so out-of-module Kotlin files were never an intentional input.

### 3.2 Analysis API entry point: shared helper

A new `parser/KotlinAnalysisHelpers.kt` exposes one chokepoint:

```kotlin
internal inline fun <T> withKtAnalysis(
    file: KtFile,
    block: KaSession.(KtFile) -> T
): T? {
    return try {
        analyze(file) { block(file) }
    } catch (e: ProcessCanceledException) {
        throw e
    } catch (e: Exception) {
        logger.warn("Analysis API failure for ${file.virtualFilePath}", e)
        null
    }
}
```

All Kotlin analyzers and the Kotlin symbol extractor go through it. Failures (F2 in §6.1) collapse to `null`; analyzers interpret `null` as "skip this file." `ProcessCanceledException` is rethrown unconditionally per V1.2's hardening rule.

### 3.3 Threading

Read action wraps `analyze { }` block. Non-negotiable — Analysis API mandates a read action.

```kotlin
ApplicationManager.getApplication().runReadAction<List<Issue>> {
    val ktFile = PsiManager.getInstance(project).findFile(vf) as? KtFile
        ?: return@runReadAction emptyList()
    withKtAnalysis(ktFile) { analyzeNullSafety(it) } ?: emptyList()
}
```

Cancellation inside `analyze { }` is platform-driven: the platform checks at PSI boundaries automatically. We do not add explicit `ProgressManager.checkCanceled()` calls; we still rethrow PCE in `catch` blocks per V1.2.

### 3.4 New `KotlinAnalyzer` base class

V1.2 has the `extension == "kt"` filter duplicated in every Kotlin analyzer. V1.3 extracts a tiny base:

```kotlin
abstract class KotlinAnalyzer : Analyzer {
    final override fun analyze(context: AnalysisContext): List<Issue> {
        val out = mutableListOf<Issue>()
        for (file in context.parsedFiles.filter { it.extension == "kt" }) {
            val ktFile = ApplicationManager.getApplication().runReadAction<KtFile?> {
                PsiManager.getInstance(context.project).findFile(file.virtualFile) as? KtFile
            } ?: continue
            try {
                val issues = ApplicationManager.getApplication().runReadAction<List<Issue>> {
                    withKtAnalysis(ktFile) { analyzeKtFile(ktFile, file, context, this) } ?: emptyList()
                }
                out.addAll(issues)
            } catch (e: Exception) {
                if (e is ProcessCanceledException) throw e
                logger.warn("$name failed for ${file.path}", e)
            }
        }
        return out
    }

    abstract fun analyzeKtFile(
        ktFile: KtFile,
        parsedFile: ParsedFile,
        context: AnalysisContext,
        session: KaSession
    ): List<Issue>
}
```

Four analyzers extend it: rewritten `KotlinNullSafetyAnalyzer`, plus the three new ones.

### 3.5 Fixer interface extension

V1.3 adds an optional PSI-aware hook to `Fixer`. Default returns `null`; existing TS/JS fixers compile unchanged.

```kotlin
interface Fixer {
    val ruleId: String
    val description: String
    fun canFix(issue: Issue): Boolean = issue.ruleId == ruleId
    fun generateFix(issue: Issue, fileContent: String): CodeFix?

    /**
     * Optional PSI-driven fix path. Tried by FixApplicator before generateFix(...).
     * Returning null means "fall back to text-based path."
     * The parameter is `PsiFile` (not `KtFile`) to keep Fixer.kt language-neutral;
     * Kotlin fixers cast internally.
     */
    fun generateFixFromPsi(issue: Issue, file: PsiFile): CodeFix? = null
}
```

`FixApplicator` runs the new method first inside a read action; falls back to `generateFix(issue, fileContent)` when it returns null. The actual document edit still goes through the existing text-based path (preserving V1.0's text-undo guarantees) — the PSI hook supplies *better-derived* `originalCode`/`fixedCode` strings, not a separate mutation pipeline.

### 3.6 Dependencies

`bundledPlugin("org.jetbrains.kotlin")` already brings in `org.jetbrains.kotlin.analysis.api.*`. **No production `build.gradle.kts` dependency changes.** The test classpath gains one entry to bring `KotlinLightProjectDescriptor` into scope; the exact `TestFrameworkType` constant is resolved during implementation (see OQ1 in §10).

## 5. Data flow

### 5.1 Cold start (project-wide analysis)

```
1.  User → Tools → Aegis Debug → Analyze Project (Ctrl+Alt+G)
2.  AnalyzeProjectAction → GhostDebuggerService.analyze()
3.  FileScanner walks project → List<ParsedFile> (virtualFile + raw content)
4.  SymbolExtractor.extract(parsedFile) per file:
      - .kt: KotlinPsiSymbolExtractor.extract():
            runReadAction { PsiManager.findFile(virtualFile) → KtFile }
            walk PSI for functions/classes/imports/properties (existing logic)
            withKtAnalysis(ktFile) {
                for each KtNamedFunction:
                    returnType  = expressionType().render()
                    paramTypes  = valueParameters.map { it.type.render() }
            }
      - .java: JavaPsiSymbolExtractor.extract() — populates the same fields from PSI
      - .ts/.js: TsJsRegexSymbolExtractor — leaves new fields empty
5.  AnalysisEngine.runAnalysis(context)
6.  Two-phase static pass (V1.1 architecture, unchanged):
      Phase 1 (early): PsiSyntaxAnalyzer, CompilationErrorAnalyzer
      Phase 2 (late):  for each KotlinAnalyzer subclass:
          (read action + withKtAnalysis is built into the base class)
          analyzeKtFile(ktFile, parsedFile, ctx, kaSession) → List<Issue>
7.  Optional AI pass (Ollama / OpenAI) — unchanged
8.  AnalysisResult → annotator + tool window + NeuroMap
      - NeuroMap consumes ParsedFile.functions[].returnType when non-null
      - AI prompt builder includes returnType/paramTypes in detectIssues prompt
        for Kotlin/Java files
```

### 5.2 Single-file re-analysis (V1.2 cascade preserved)

```
1.  User edits SomeFile.kt → debounce → reanalyzeFile(SomeFile.kt)
2.  Static-only path (V1.2): re-runs phase 1 + phase 2 for the changed file
3.  V1.2 cascade: ProjectGraph dependents → reanalyze (static-only,
    capped at maxDependentsToReanalyze, default 20)
4.  Each cascaded file goes through §5.1 step 6 — fresh KaSession per file,
    no cross-file state.
```

The Analysis API session **does not** persist across files. Each file's analysis is independent. This matches V1.2's per-file fan-out and avoids stale-session hazards.

### 5.3 Fix application

```
1.  User clicks Apply Fix on a Kotlin issue
2.  FixApplicator.apply(issue):
      runReadAction {
        ktFile = PsiManager.findFile(...)
        codeFix = fixer.generateFixFromPsi(issue, ktFile)
                 ?: fixer.generateFix(issue, fileContent)   // existing path
      }
3.  WriteCommandAction.runWriteCommandAction { document.replaceString(...) }
4.  PSI validity check (existing — V1.0): commit document, re-parse,
    abort if invalid
5.  Native undo registers the change atomically
```

The new Kotlin fixers use PSI for **decision-making** (find the right node, derive the safe replacement) but the actual edit goes through the existing text-replace path. This preserves V1.0's text-based undo guarantees and avoids introducing a parallel PSI-mutation pipeline.

### 5.4 What's unchanged

- `Issue` shape, `IssueSource.STATIC`, `confidence` model
- ExternalAnnotator surface in plugin.xml
- AI prompt schema (new fields slot into existing function entries)
- Cancellation contract (PCE rethrows, V1.2 rule)
- Engine status pill behavior

## 6. Error handling & graceful degradation

### 6.1 Failure mode taxonomy

| # | Failure | Where | Behavior |
|---|---|---|---|
| F1 | `virtualFile` doesn't resolve to a `KtFile` (scratch file, out-of-module file) | `PsiManager.findFile() == null` or cast fails | Return empty `List<Issue>`. **No fallback to synthesized PSI** (deleted). Log INFO once: `Kotlin PSI unavailable for $path; skipping Aegis analysis`. |
| F2 | `withKtAnalysis` throws (Analysis API internal exception) | Caught in helper | Helper returns null; analyzer skips file. Log WARN with stack trace. PCE rethrown unconditionally. |
| F3 | Expression has `KaErrorType` (unresolved symbol, broken type) | Inside an analyzer | Treat as "can't decide" — don't flag. Per-expression skip, not per-file. One bad import doesn't disable the whole file's analysis. |
| F4 | File has syntax/compilation errors | V1.1 two-phase early gate | Kotlin analyzers never run. Existing contract. |
| F5 | `ProcessCanceledException` | Anywhere | Rethrown immediately. Every new `catch (e: Exception)` block has the V1.2-mandated PCE rethrow. |
| F6 | User on IDE < 2024.3 | Install time | `sinceBuild = "243.0"` — Marketplace and plugin manager refuse to install. No runtime concern. |
| F7 | `generateFixFromPsi` throws | `FixApplicator` | Caught, logged WARN, falls through to text-based `generateFix`. Existing AI-fallback path still applies if both fail. |

### 6.2 Centralized via `withKtAnalysis`

Analyzers never see Analysis API exceptions. `withKtAnalysis` returns `null` on any non-PCE failure; analyzers always interpret null as "return empty list."

### 6.3 Per-analyzer "type unknown" handling (F3)

Each new analyzer documents its `KaErrorType` decision matrix in KDoc. Example for unsafe-cast:

```
if (cast.targetType is KaErrorType)         → don't flag
if (receiver.expressionType is KaErrorType) → don't flag
if (target is supertype of receiver)        → don't flag (upcast, safe)
if (target is subtype of receiver)          → flag (downcast without `as?`)
otherwise                                   → don't flag
```

Conservative-miss bias: when in doubt, don't flag. False positives erode trust faster than false negatives.

### 6.4 Test coverage for failure modes

Each F-case gets at least one test:

- F1: VirtualFile that resolves to no module → analyzer returns empty
- F2: `withKtAnalysis` mocked to throw → analyzer returns empty, log captured
- F3: Code with an unresolved import → analyzer skips affected expressions, still flags unaffected ones in the same file
- F4: Deliberate syntax error → broken-file gate fires (V1.1 contract)
- F5: Cancellation during `analyze { }` → PCE rethrown
- F7: Throwing PSI fixer → falls back to text fixer cleanly

### 6.5 What we don't add

- No retry logic. If `analyze { }` fails once, it fails again.
- No user-visible error notification. Failures are operator-grade information.
- No telemetry/counters. IDE log is the only sink.
- No fallback to V1.2 name-matching. That code is gone.

## 7. Testing strategy

### 7.1 Test infrastructure

**One new test base class:** `AegisKotlinAnalysisTestCase` extends `BasePlatformTestCase`:

- Overrides `getProjectDescriptor()` to return `KotlinLightProjectDescriptor.INSTANCE` (or equivalent — see OQ2 in §10). This brings Kotlin stdlib onto the light-fixture classpath, which is required for `expressionType()` to resolve to anything other than `KaErrorType`.
- Provides `analyze(source: String): List<Issue>` helper.
- Provides `expectFinding(source, ruleId, line)` and `expectNoFinding(source)` assertions.

**One new fixer base class:** `AegisKotlinFixerTestCase` extends `AegisKotlinAnalysisTestCase`:

- Provides `fix(source, ruleId): String` that runs analyzer → picks issue → generates fix → returns fixed source. Tests assert verbatim.

### 7.2 Test scope per file

| File | Test count target | Coverage |
|---|---|---|
| `KotlinNullSafetyAnalyzerTest` | 25-30 (vs. ~12 today) | All V1.2 cases stay green (regression bar). New: type-inferred nullables, smart-cast windows, `lateinit` with explicit assignment, generic bounds. Includes canary. |
| `KotlinUnsafeCastAnalyzerTest` | 12-15 | Downcast flagged; upcast not flagged; `KaErrorType` cases not flagged; smart-cast-already-applied cases not flagged. |
| `KotlinTypeMismatchAnalyzerTest` | 10-12 | `val x: Int = ""` flagged; assignable types (Int→Number) not flagged; nullable mismatch flagged; generic invariance respected. |
| `KotlinRedundantLetAnalyzerTest` | 8-10 | Smart-cast-confirmed redundant let flagged; let with side effects not flagged; let with multiple statements not flagged. |
| `KotlinUnsafeCastFixerTest` | 6-8 | Fix shape preserved across return-type contexts; declines on variable-position casts; preserves indentation. |
| `KotlinRedundantLetFixerTest` | 5-7 | `x?.let { it.foo() }` → `x.foo()`; chained access preserved; declines on multi-statement lets. |
| `KotlinPsiSymbolExtractorTest` | +6-8 (existing 18 stay green) | `returnType`/`paramTypes` populated; canary asserts `String?` not `String`. |
| `JavaPsiSymbolExtractorTest` | +4-6 | Same enrichment verification for Java. |

**Total new tests:** ~70-90. **Final green bar:** ~190-210 (V1.2 had 117).

### 7.3 Canary tests

Each new analyzer has at least one canary that asserts a finding from a case the V1.2 name-matcher would have missed. If `KotlinLightProjectDescriptor` silently fails to load stdlib (so every type becomes `KaErrorType`), every analyzer's canary fails — that's the alarm for "tests pass because resolution silently broke" (R3 in §9).

```kotlin
fun testCanary_typeInferredNullableMissedByOldAnalyzer() {
    val src = """
        fun fetch(): String? = null
        fun run() {
            val x = fetch()
            println(x.length)   // line 4 — expected finding
        }
    """.trimIndent()
    expectFinding(src, "AEG-NULL-KT-001", line = 4)
}
```

### 7.4 Performance smoke

`AnalysisEnginePerfSmoke` (existing) gains one Kotlin entry: analyze a 100-file synthetic Kotlin project, assert <2× regression vs. V1.2 baseline.

### 7.5 What we don't add

- No mutation testing (out of scope).
- No fuzzing (out of scope).
- No heavy fixture / sandbox project tests (light fixture suffices).
- No platform-version-specific test matrix (`verifyPlugin` covers cross-version).

## 9. Risks

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|

## 11. Explicit non-goals for V1.3

V1.3 is **not**:

- Language breadth (Python is V2)
- Fixer breadth beyond the two new ones (V3)
- IDE-native integrations: Problems window, Alt-Enter intentions, inspection profile (V2)
- Streaming AI responses (V2)
- Debug-time UX, profiler integration, runtime validation (V2/V4)
- Telemetry or usage counters (privacy principle)
- Custom rule authoring (V3)
- Cross-repo / team scale (V5)
- Deprecation warnings or in-IDE notices for users on < 2024.3 — JetBrains Marketplace and the IDE plugin manager refuse installation based on `sinceBuild`; we do not ship our own messaging

### Out-of-scope cleanups noticed during exploration

These are tempting but stay out:

- `plugin.xml` line 4 still says `<version>1.1.2</version>`; the Gradle plugin overrides at build time, so it is cosmetic. Optional follow-up commit on `main` post-1.3, not part of V1.3.
- `change-notes` block for older versions stays as-is in `plugin.xml`; we *append* 1.3.0 notes, not rewrite history.

## 12. Acceptance criteria

V1.3.0 ships when:

1. `./gradlew check` passes clean (compile + all tests green)
2. `./gradlew verifyPlugin` reports Compatible against IU 2024.3.2.2 / 2025.1 / 2026.1
3. Manual smoke in IntelliJ 2024.3.2 Community: K2 incompatibility banner is gone, Analyze Project runs without exceptions in the IDE log, each of the four Kotlin analyzers produces at least one expected finding on a prepared sample project, both new fixers apply cleanly with native undo
4. Total green test bar ≥ 190
5. Performance smoke shows <2× regression vs. V1.2 baseline
6. CHANGELOG.md 1.3.0 section is final (analyzer counts, fixer counts, link to this design doc)
7. `v1.3-k2-migration` branch merges to `main` as a single merge commit
